Demonstrates the `lupi` compatibility system: a small, self-authored cart (`tiny_quest`) running unmodified inside newbase from source form. No Lupi devkit/compiler involved. It exercises some common graphics primitives, presenting a simple JRPG-style demo.

Checkout the "Lupi Debug" window (F10), for `lupi` system internals and controls.

`scene.lua` calls `lupi_start("res/lupi_demo/tiny_lupi.yaml")`, an RTTI-exposed function on the `lupi` system (see `src/lupi/lupi.cpp`). Switching to another demo calls `lupi_stop()` automatically via `lupi::on_scene_change()`.

The cart runs in its own, fully isolated `lua_State`; it can't see or touch anything in this scene's Lua environment, and vice versa. Game sources ship no compiled assets (no `sprites.lua`/`palette.lua`/compiled maps). Those are normally generated by Lupi's own build pipeline. The `lupi` system reimplements that step itself at boot time: every `*.png` under the cart directory is
auto-discovered and palettized into `Sprites`/`Palette`, any `*.json` Tiled export anywhere in the cart is compiled into the same table shape the real pipeline produces, and `require()` is replaced outright to serve all of this without touching disk via Lua's own file I/O. See `doc/system_lupi.md` for the full picture.

The engine's default input actions, which represent a standard joypad layout, are mapped to a virtual SNES controller that the `lupi` system uses, mirroring how the real Lupi console gets its inputs.
